# 从实际需求到第三方控制：开发过程与源码地图

[返回主页](../README.md) · [协议](PROTOCOL.md) · [使用指南](USAGE.md)

## 1. 起点：设备买到了，但控制入口受手机环境限制

目标不是增加散热器原本没有的能力，而是在自己的手机 / PC 环境中控制已有的功率和灯效，并读取设备状态。作者现已确认 Android 自用版可以正常使用。

## 2. 为什么“写入成功”还不够？

早期先枚举 BLE 服务、写特征和通知特征，再尝试候选数据。这个阶段遇到的关键现象是：蓝牙层能接受数据，设备却不一定有实际反应。

因此后续工作转向官方操作过程的 HCI 抓包：观察正常连接时先发什么、设备回什么，再看功率 / 灯效操作与设备通知之间的关系。最终日常控制聚焦到 AF07 写入、AF08 接收，而不是继续向所有候选特征盲目试写。

## 3. 从抓包到值表

将历史记录中的认证、初始化、属性写入和主动通知分开理解，并与设备按键操作逐项对照。值得保留的纠错过程包括：

| 曾遇到的问题 | 最终采用的认识 |
| --- | --- |
| 把所有认证载荷当成每次都变化 | 所观察记录中的 c0 与 c1 不同；只能在证据范围内讨论固定重放，不称为通用破解 |
| UI 下标直接当成功率值 | 静音与智能存在映射交换，不能直接按 0、1、2 套用 |
| 只凭早期抓包推断灯效名称 | 后期结合物理按键核对，采用当前五档值表 |
| 混用大端 / 小端 | 外层长度与控制值分别处理；灯效值为两字节 LE |
| 把设备状态和上次点击混为一谈 | 通过 F4 设备回报更新状态，不能仅凭发送日志判断执行成功 |

不公开完整手机抓包，避免带出个人设备地址和其他应用 / 设备通信。原始开发记录中的早期错误结论保留在个人归档，本项目文档采用后续修正后的认识，并指出尚未统一的字段语义。

## 4. Python：控制核心与交互分离

[`cooler_ctrl.py`](../cooler_ctrl.py) 同时提供 `XiaomiCoolerController` 和 CLI，包含扫描、保存设备地址、连接、服务枚举、认证序列、功率 / 灯效写入、通知监听与原始写入诊断。

[`xiaomi_cooler_gui.py`](../xiaomi_cooler_gui.py) 使用 PyQt5，实际导入的控制核心是 `cooler_ctrl.py`；文件开头仍保留早期版本名注释，不应据此误判当前依赖。

```text
Qt 主线程：界面、按钮、状态卡片
    │ run_coroutine_threadsafe
后台线程：asyncio event loop → Bleak → Windows BLE
    │ Qt signals
Qt 主线程：更新设备列表、温度、功率、灯效
```

GUI 扫描列表优先排列已知设备名称，并显示地址和信号强度；状态回报更新下拉框时阻断 signal，避免“更新显示”再次触发控制写入。这些是实际源码中的交互细节，不只是一个静态界面。

## 5. Android：独立的原生 App

Android 版不是把 PC 窗口或网页封装进手机。它使用 Kotlin、Jetpack Compose 和 Android BluetoothGatt API。

```text
MainActivity：入口、权限及 BLE 硬件检查
        ↓
MainScreen：Compose UI → CoolerViewModel：StateFlow、设备列表、日志
        ↓
BleManager：扫描 / GATT / 通知 / 写入
        ↕
CoolerProtocol：帧常量、模式编码、状态解析

CoolerService：前台通知、状态显示、快捷操作
CoolerGlobal：通知操作与界面共享的当前状态 / BLE 管理器引用
```

通知按钮通过 Service PendingIntent 进入前台服务，再调用现有功率 / 灯效操作；文件 `NotificationActionReceiver.kt` 中还保留 BroadcastReceiver 辅助入口，但当前 manifest 没有注册它，不能把文件名当成实际按钮分发路线。

本机 Git 历史记录了扫描兼容、白色卡片界面、连接后收起列表、状态更新及通知栏等迭代。本次同步把这些已有提交发布到 GitHub，**没有额外重写 BLE 或改变设备控制逻辑**。

## 6. Web：另一种控制入口

[`cooler_web.html`](../cooler_web.html) 使用浏览器 Web Bluetooth、系统设备选择器和原生 JavaScript，包含功率 / 灯效按钮、状态卡片及日志。

它与 Android 使用同一组协议认识，但有独立的连接状态与写入实现。当前历史代码存在初始化门控问题，见 [使用指南](USAGE.md#4-web-bluetooth)。保留源码是为了展示实现过程，不把它包装成已经完成新一轮适配的网页产品。

## 7. 哪些是实际成果？

- 原生 Android 应用，以及作者的正常使用确认。
- 三档功率、五种灯效、温度 / 模式回报及通知栏操作的源码实现。
- Python CLI 与 PyQt GUI，分离控制核心、异步 BLE 操作与 UI。
- Web Bluetooth 历史实现。
- GATT 通道、控制值表、状态解析和开发纠错记录。
- 可下载 APK、匹配源码与校验值，便于别人检查和复现。

这些成果体现设备通信分析、问题排查、多端实现和真实需求落地；不延伸为硬件设计、设备固件开发、密码学算法创新或全机型兼容认证。

## 8. 验证信息如何阅读

| 证据 | 能支持什么 | 不单独支持什么 |
| --- | --- | --- |
| 作者 Android 正常使用确认 | 指定自用环境中的功能可用 | 所有手机 / 固件兼容 |
| 原始手机截图 | 真实 UI、控件和显示布局 | 截图当时成功连接、日志命令实际执行 |
| Kotlin / Python / JS 源码 | 实现方式及功能入口 | 长时间稳定性或全部异常场景通过 |
| 历史 HCI / 按键核对记录 | 已观察帧与映射分析 | 通用密钥、解密算法或未测的固件行为 |
| APK 构建 / 签名 / 哈希检查 | 安装包结构、版本和文件一致性 | 实机控制回归或测温精度 |

开发阶段使用过 WorkBuddy 等 AI 编程辅助工具。对于这类个人工程项目，工具参与不等于功能自动成立；设备操作、后期按键核对和作者使用确认是不同层次的证据，需要分别保留。
