## 1. 我想解决的问题

散热背夹已经买到，但非澎湃系统的小米 / Redmi，以及其他品牌 Android 手机用户，可能缺少方便可用的控制入口。我的出发点是让同样持有 R01P-M 的人，在现有手机上也能调节功率和灯效、查看状态，而不必依赖系统专属面板。现在我已在自己的 Android 手机上正常使用这个 App。

## 2. 写入成功，为什么设备却没反应？

我先从 BLE 服务、写特征和通知特征入手，枚举设备的通信入口，再尝试候选数据。最初遇到的问题是：蓝牙层显示写入成功，设备却没有相应动作。

于是我转向分析正常控制过程的 HCI 抓包：连接时先发什么、设备返回什么、切换功率和灯效后又会出现什么通知。对比这些过程后，日常控制路径逐步明确为 AF07 写入、AF08 接收。

## 3. 从抓包到可用的值表

我把认证、初始化、属性写入和主动通知分开梳理，再与设备按键逐项对照。这个过程中，有几处判断经过实际操作后的修正：

| 遇到的问题 | 后续采用的认识 |
| --- | --- |
| 把所有认证载荷当成每次都变化 | 记录中的 c0 与 c1 不同；固定重放只在观察范围内讨论 |
| 用 UI 下标直接表示功率 | 静音和智能的属性值需要交换映射 |
| 只凭早期抓包推断灯效名称 | 结合后期物理按键对照，采用当前五档值表 |
| 混用大端与小端 | 外层长度与控制值分别处理，灯效值使用两字节 LE |
| 把最近一次点击当成设备状态 | 根据 F4 回传更新显示，发送日志不单独代表执行成功 |

完整抓包留在本地，公开文档只整理与本设备相关的帧结构和值表。早期被修正的结论没有直接搬到这里；尚未确定的字段保留实际代码用法及疑问。

## 4. Python：分开控制核心与界面

[`cooler_ctrl.py`](../cooler_ctrl.py) 提供 `XiaomiCoolerController` 和 CLI，包含扫描、保存设备地址、连接、服务枚举、认证序列、模式控制、通知监听及原始写入诊断。

[`xiaomi_cooler_gui.py`](../xiaomi_cooler_gui.py) 使用 PyQt5，实际导入 `cooler_ctrl.py`；开头保留的早期版本名注释不是当前依赖。

```text
Qt 主线程：按钮、设备列表、状态卡片
        │ run_coroutine_threadsafe
后台线程：asyncio event loop → Bleak → Windows BLE
        │ Qt signals
Qt 主线程：更新温度、功率、灯效和连接状态
```

扫描列表优先排列已知设备名称，并显示地址和信号强度。状态回报更新下拉框时阻断 signal，避免更新显示又触发一次控制写入。这些处理让窗口显示和 BLE 操作能够衔接起来。

## 5. Android：做成手机上直接使用的 App

Android 版使用 Kotlin、Jetpack Compose 和 BluetoothGatt API，不是把 PC 窗口或网页封装进手机。

| 模块 | 职责 |
| --- | --- |
| `MainActivity` | 应用入口、权限与 BLE 硬件检查 |
| `MainScreen` | Compose 控制界面 |
| `CoolerViewModel` | StateFlow、设备列表、日志和界面事件 |
| `BleManager` | 扫描、连接、服务发现、通知与 GATT 写入 |
| `CoolerProtocol` | 帧常量、功率 / 灯效编码、F4 状态解析 |
| `CoolerService` / `CoolerGlobal` | 通知栏入口、共享状态和快捷操作 |

![Android 控制请求与状态回传](images/android-command-feedback.png)

[查看矢量图 / Open SVG](images/android-command-feedback.svg)

通知按钮通过 Service PendingIntent 进入前台服务，再调用已有控制操作。`NotificationActionReceiver.kt` 还保留一个 BroadcastReceiver 辅助入口，但当前 manifest 没有注册它，实际通知按钮不走这个接收器。

我在 Android 版继续调整了扫描兼容、白色卡片界面、连接后收起列表、状态更新和通知栏操作。对应迭代可以在 Git 历史中查看；这次整理没有额外改写 BLE 或控制逻辑。

## 6. Web：保留另一种实现过程

[`cooler_web.html`](../cooler_web.html) 使用 Web Bluetooth、系统设备选择器和原生 JavaScript，包含模式按钮、状态卡片和日志。

它与 Android 使用同一组协议认识，但连接状态和写入实现独立。当前历史代码有初始化门控问题，详见 [使用指南](USAGE.md#4-web-bluetooth)。日常使用以 Android 版为主，Web 源码用于保留实现过程。

## 7. 这个项目留下的成果

- 我正在 Android 手机上使用的原生应用。
- 三档功率、五种灯效、设备状态和通知栏操作。
- Python 控制核心、CLI 与 PyQt GUI。
- Web Bluetooth 历史实现。
- GATT 通道、模式值表、状态解析和纠错记录。
- 可下载 APK、对应源码及校验文件。

它对我最有价值的地方，是把一个实际遇到的问题，经过通信分析和反复核对，做成了自己可以日常使用的工具。

## 8. 使用范围与开发辅助

Android 自用环境可以正常工作；我还没有覆盖所有手机和固件。抓包、代码、截图与安装包校验分别回答不同问题：截图能看界面，源码能看实现，设备操作才能验证对应功能。

我还使用 Type-C 功率测试仪做过实机核对，确认控制不是只改变界面文字。功率控制与仪表观察相对应，灯效则按设备实际显示检查；目前没有在仓库公开具体功率表或原始测量记录，所以不补写瓦数和误差指标。

温度准确度、灯效第二字节的完整含义及跨固件认证兼容性仍有待进一步核对。项目不涉及固件修改、硬件设计或通用密钥破解。

开发过程中，我使用了 WorkBuddy 等 AI 编程辅助工具进行分析、代码实现和资料整理；设备操作、按键对照及实际使用也保留在开发记录中。这里重点记录问题如何被逐步解决，而不是把辅助工具的推断当成已经完成的实验。
