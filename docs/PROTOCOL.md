## GATT 通道

UUID 均使用蓝牙标准基础尾段 `-0000-1000-8000-00805f9b34fb`。

| 短 UUID | 完整前缀 | 用途 |
| --- | --- | --- |
| AF00 | `0000af00` | 厂商自定义服务 |
| AF07 | `0000af07` | 认证 / 初始化 / 控制写入；当前 Android 使用 write-without-response |
| AF08 | `0000af08` | 接收设备应答和主动状态通知 |

设备名筛选只是扫描辅助，服务与特征值才是代码使用的通信入口。底层 GATT 接受写入不代表设备应用层接受了命令。

## MMA 帧

历史资料将此命名为 MMA 私有帧。观察到的基本格式：

```text
FE DC BA | header | opcode | payload_length (2B, BE) | payload | EF
```

| 字段 / 操作 | 当前认识 |
| --- | --- |
| `C0` / `C1` | 历史主机发送帧中观察到的不同交互头；不把头位的全部语义当成已确认 |
| `01` | 应答帧中观察到的头 |
| `81 F4` | 设备主动状态上报 |
| `50` / `51` | 历史认证交互 |
| `F2` | 属性控制 |
| `F3` | 历史记录中出现的属性查询；当前日常控制路径主要使用 F4 状态 |
| `02` / `09` / `0C` | 初始化 / 设备信息查询序列 |

长度字段与 F2 属性值的字节序不同：**外层载荷长度为大端，功率 / 灯效值为小端**。载荷内部的 `EF` 不应被不加区分地当成帧尾。实际通知可能包含多个子帧，不能把每次通知回调都想当然视作唯一完整业务消息。

## 三档功率

| UI 名称 | 模式值 | 两字节 LE |
| --- | --- | --- |
| 静音 / LOW | `0x0001` | `01 00` |
| 智能 / MID | `0x0000` | `00 00` |
| 极寒 / HIGH | `0x0002` | `02 00` |

这不是 UI 下标直接递增：静音与智能的属性值顺序相反。当前 Android 构造帧：

```text
FE DC BA C1 F2 00 06 01 04 00 40 [value_L] [value_H] EF
```

`40` 为功率属性。历史 HCI 对部分功率写入有直接样例，后期记录又结合物理按键 / 设备反应核对映射；不能声称每一档都有同范围的原始抓包证据。

## 五种灯效

| UI 名称 | 属性值 | 两字节 LE |
| --- | --- | --- |
| 彩虹 | `0x0001` | `01 00` |
| 呼吸 | `0x0202` | `02 02` |
| 流动 | `0x0103` | `03 01` |
| 常亮 | `0x0104` | `04 01` |
| 关闭 | `0x0000` | `00 00` |

当前 Android 构造帧：

```text
FE DC BA C1 F2 00 06 02 04 00 42 [value_L] [value_H] EF
```

`42` 为灯效属性。表格采用当前实现及后期物理按键核对记录，不采用早期报告中已被修正的灯效表。第二个值字节的完整含义尚未确认，不擅自命名为速度、亮度或其他参数。

**注意字段争议：** 不同历史记录曾把 F2 载荷首字节解释为序号或子包标识。当前 Android 的功率帧固定使用 `01`、灯效帧固定使用 `02`；Web 实现会修改该字节。本文按各端现有代码描述，不宣称已经建立跨固件通用规则，也不替它们统一改写协议。

## F4 状态

观察到的单属性通知示意：

```text
FE DC BA 81 F4 00 05 [seq] 03 00 3F [temperature] EF
FE DC BA 81 F4 00 05 [seq] 03 00 40 [power] EF
FE DC BA 81 F4 00 06 [seq] 04 00 42 [light_L] [light_H] EF
```

- 温度 `003F`：有符号 8 位数，大于 127 的原始字节按负值解释。它是设备传感器上报，不等于手机芯片温度。
- 功率 `0040`：按上面的功率值映射。
- 灯效 `0042`：按两字节 LE 组合后查表，不只看第一个字节。
- `03` / `04` 与后续属性条目长度对应；不能把它们直接写成功率或灯效编号。

物理按键产生的设备状态变化也可进入这一通知路径。当前 Android 通过 F4 解析结果更新 ViewModel；Python GUI 通过后台监听 / 状态处理和 Qt signal 更新显示。

## 认证与初始化

1. 历史日志中观察到 c0 和 c1 两类交互。后期记录发现，在所观察的记录中 c0 挑战载荷可重复，而 c1 载荷随会话变化。
2. 后期实机记录称仅使用 c0 后仍可控制；**当前发布源码并未依此删除固定 c1 重放，仍保留两段序列**。这是历史记录与当前实现的区别。
3. 固定样例在特定设备上的可用性，不等于知道通用密钥或实现了动态挑战响应；不称为“破解全部小米加密”。
4. F4 通知在历史记录中可在未完成控制认证时出现。因此“收到了温度”不能单独证明认证成功，更不能证明某条 F2 已执行。
5. 我已在自己的 Android 手机上正常使用该软件，但当前代码仍不是逐步严格验证全部应答的协议状态机。调试其他设备时，应结合硬件反应和状态回传判断，而不只看“Auth complete”日志。
